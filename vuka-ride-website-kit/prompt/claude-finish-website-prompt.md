## Your role and the situation

You are a senior frontend engineer finishing the marketing website for **Vuka Ride**, a ride-hailing app for Africa (tagline: *Moving Africa Forward*; "Vuka" means "rise / wake up").

**Important context:**
- **The mobile app is already built and finished.** Do not build, change or mock app features. It will be linked to this website later, so everything that points at the app must be configurable and clearly marked, not hard-coded.
- The website's frontend has a first draft (generated by a design tool). Your job is to review it, complete it, fix it and make it launch-ready. Where something is missing, build it. Where something is wrong, fix it.
- There is no backend for this site yet. Forms must work in **mock mode** by default and be ready to connect to a real API later through one environment variable.

## First, do this

1. Read the whole repo. Summarise in 10 lines or fewer: the stack, the pages that exist, components, and what is missing or broken against the checklist below. Do not ask me questions you can answer from the code.
2. Create a task list from the checklist, then work through it. Commit in small, logical steps with clear messages if this is a git repo.
3. If the stack is not Next.js (App Router) with TypeScript and Tailwind, keep the existing stack. Do not rewrite it. Adapt the instructions below to it.

## Brand (use exactly)

Colours: deep `#064E2B`, green `#0B8F3E`, green-600 `#097235` (use for buttons and small white-on-green text), night `#04371F`, orange `#F57C00` (large text, icons and graphics only), sun `#FFB300`, ink `#111827`, slate `#4B5563`, mist `#F5F7F5`, leaf `#D1FAE5`. Font: Poppins (400, 500, 600, 700).

Rules: never white text on `#0B8F3E` at small sizes (4.2:1); never orange or white-on-orange for small text (2.7:1); gold buttons use ink text. Balance is roughly 40% deep green, 30% white and mist, 20% green, 10% orange and gold. Cards 24px radius, buttons pill-shaped, touch targets at least 44px.

Logo: a bold V (the road) with a gold sun rising in its mouth. Use the files in `public/images/` (`logo-horizontal.svg`, `logo-horizontal-white.svg`, `mark-color.svg`, `mark-white.svg`, `app-icon-rounded.svg`) and the `VukaMark` / `VukaLogo` components. No emoji anywhere; use `lucide-react` icons.

## Checklist: app linking (the app comes later)

- Create one config module (for example `lib/site-config.ts`) that reads from environment variables listed in `.env.example`: `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_GOOGLE_PLAY_URL`, `NEXT_PUBLIC_APP_STORE_URL`, `NEXT_PUBLIC_APP_DEEP_LINK`, `NEXT_PUBLIC_API_BASE_URL`, support email, phone and WhatsApp.
- Every store button, "Get the app" button and "Apply to drive" link must read from that config. No store URL anywhere else in the code.
- If a store URL is empty, the button must still render, point to `/download`, and the `/download` page must show a friendly "Coming soon" state with an email or WhatsApp sign-up for launch news (mock mode). When the URL is set, the button goes straight to the store.
- `/download` should detect the visitor's OS in the browser: Android goes to Google Play, iOS to the App Store, desktop shows both buttons plus a QR placeholder (generate a QR from the config URL with a small library when a URL exists).
- Add a clearly commented `// TODO: link to the finished app` at each integration point, and list them all in `README.md` under "Linking the app".
- Add placeholders for `/.well-known/assetlinks.json` (Android App Links) and `/.well-known/apple-app-site-association` (iOS Universal Links) with comments explaining what to fill in. Do not invent package names or team IDs.

## Checklist: forms

Apply to: driver application, contact, delete-account request, newsletter or launch notify.

- `react-hook-form` plus `zod`. Inline errors, accessible labels, error summary for screen readers, disabled and loading state while submitting, success panel, and a general error state with retry.
- South African mobile number validation (accept +27 and 0 prefixes; normalise to +27).
- Honeypot field and basic time-based spam check. No CAPTCHA required yet; leave a comment where one would go.
- One `submitForm(kind, data)` function. If `NEXT_PUBLIC_API_BASE_URL` is empty, run in **mock mode**: log the data to the console, wait 600ms, return success. If set, POST JSON to `${API_BASE}/forms/{kind}` and handle errors. Document the expected request shape in the README.
- Never store personal data in `localStorage`. Never log personal data in production mode.

## Checklist: quality

- **Responsive:** perfect at 360, 390, 768, 1024 and 1440px. No horizontal scroll, no clipped text, no overlap. Test by actually running the dev server and checking, not just by reading code.
- **Accessibility:** WCAG 2.1 AA. Keyboard navigation for menu, sheet and accordion, visible focus rings, correct landmarks, labelled icon buttons, alt text, `prefers-reduced-motion` respected, skip-to-content link. Target Lighthouse accessibility 95 or more.
- **Contrast:** audit every text and background pair against the brand rules above and fix failures.
- **Performance:** `next/image` for raster images, fonts via `next/font` with `display: swap`, no unused dependencies, no layout shift, Lighthouse performance 90 or more on mobile. Lazy-load below-the-fold sections.
- **SEO:** per-page metadata (title, description, canonical, Open Graph, Twitter card), JSON-LD `Organization` and `WebSite`, `robots.txt` and `sitemap.xml` from the kit (or generated with Next's metadata routes, using `NEXT_PUBLIC_SITE_URL`). Use `public/og/og-image.png` (home and default), `og-drive.png` (drive page) and `twitter-card.png`.
- **Icons and manifest:** wire up `public/favicon.ico`, `public/icon.svg`, `apple-touch-icon.png`, `public/icons/*` and `site.webmanifest` in the document head. Set `theme-color` to `#064E2B`.
- **Security headers:** sensible defaults via `next.config` (X-Content-Type-Options, Referrer-Policy, X-Frame-Options or frame-ancestors, Permissions-Policy). No inline secrets.
- **Cookie and analytics:** do not add analytics yet. Add a small `lib/analytics.ts` stub with a comment. If any cookies or trackers are added later, a consent banner will be needed (POPIA); mention this in the README.
- **Code health:** TypeScript strict, ESLint and Prettier clean, no `any`, no dead code, components small and reusable. Add tests for the form validation schemas and the site-config logic (Vitest or the repo's existing runner), plus one Playwright smoke test per page that checks it loads and has one `<h1>` (if Playwright is practical to set up).
